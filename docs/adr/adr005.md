# ADR 005 – Implémentation du traitement des ordres

## Statut

Acceptée

## Contexte

Nous devons concevoir un système robuste de traitement des ordres clients qui respecte les contraintes suivantes :

- **Machine d'états claire** : Empêcher les ordres de se retrouver dans des états invalides
- **Type safety** : Utiliser le système de types de Rust pour garantir que tous les cas sont traités
- **Extensibilité** : Produire du code facilement extensible pour les futures évolutions
- **Performance** : Traiter un volume élevé d'ordres simultanément

## Décision

### Machine d'états pour les ordres

Le type `OrderStatus` définit tous les états possibles d'un ordre :

```rust
#[derive(Debug, Clone, Serialize, Deserialize, ToSchema)]
#[serde(tag = "status", rename_all = "snake_case")]
pub enum OrderStatus {
    /// The order has been received by the system and awaits processing
    Pending,
    /// Order has been partially filled
    PartiallyFilled {
        filled_quantity: u64,
    },
    /// Order has been completely executed
    Filled {
        date: DateTime<Utc>,
    },
    /// Order has been rejected by the system during validation or execution
    Rejected {
        date: DateTime<Utc>,
        reason: Option<String>,
    },
    /// Order has been cancelled by the user or system
    Cancelled {
        date: DateTime<Utc>,
    },
}
```

### Architecture de traitement

**File d'attente asynchrone** : Les ordres sont enfilés dans un canal Tokio (`mpsc::unbounded_channel`) et traités de manière asynchrone par des tâches concurrentes (`tokio::spawn`), avec une limite de 1000 ordres simultanés via un sémaphore. L'implémentation détaillée de la queue est décrite dans [ADR 006](./adr-006.md).

**Pipeline de traitement** :
1. Validation pré-transaction (fonds, positions, vérification utilisateur)
2. Exécution via le service market-data
3. Mise à jour du statut de l'ordre (Filled, PartiallyFilled, Rejected, Cancelled)

**États de transition** :
```
Pending → PartiallyFilled → Filled
        ↘ Rejected
        ↘ Cancelled
```

**Fonctionnalités** :
- Métriques Prometheus (longueur de file, ordres traités)
- Récupération automatique des ordres `Pending` au démarrage

## Conséquences

### Avantages

- **Type safety** : Le système de types garantit la gestion correcte de tous les états
- **Performance** : Traitement concurrent avec limitation pour éviter la surcharge
- **Traçabilité** : Horodatage des états terminaux et raisons de rejet
- **Résilience** : Récupération automatique des ordres au redémarrage
- **Observabilité** : Métriques Prometheus (file d'attente, débit)

### Inconvénients

- **Latence** : Traitement asynchrone, les clients doivent interroger le statut
- **Coordination** : Nécessite la communication entre plusieurs services
- **Limite de concurrence** : Sémaphore à 1000 peut être un goulot d'étranglement

### Risques

- **Conditions de course** : Accès concurrents à la balance et aux positions utilisateur
