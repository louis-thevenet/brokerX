# ADR 009 – Stratégie de caching multi-niveaux

## Statut

Acceptée

## Contexte

Le système doit traiter des milliers d'ordres par seconde. Sans caching, chaque ordre générerait de multiples requêtes en base de données (prix de marché, état de simulation), créant un goulot d'étranglement et augmentant drastiquement la latence.

Observation initiale : **800+ requêtes DB/seconde** lors des tests de charge.

## Décision

Implémentation de **4 niveaux de cache** distincts adaptés à chaque besoin.

## Les caches

### 1. Cache de prix de marché (Orchestrator)
**Objectif** : Éviter de requêter l'API Gateway pour chaque ordre.

**Implémentation** (`order-execution-orchestrator-service/src/clients.rs`) :
- Structure : `DashMap<String, CachedPrice>` (concurrent hash map)
- TTL : **4.5 secondes**
- Invalidation : Expiration automatique par timestamp
- Métriques : Logs "Cache HIT" / "Cache MISS"

**Justification du TTL** : Le marché se met à jour toutes les **5 secondes**, donc un cache de 4.5s garantit des prix récents tout en évitant la majorité des appels.

**Impact** : Réduit les appels API Gateway lors du traitement concurrent d'ordres sur le même symbole.

### 2. Cache de données de marché (Market Data Service)
**Objectif** : Réduire les lectures PostgreSQL des prix actuels.

**Implémentation** (`market-data-service/src/repository.rs`) :
- Structure : `moka::future::Cache<String, Arc<MarketPrice>>`
- TTL : **5 secondes**
- Capacité : 1000 symboles max
- Éviction : LRU automatique

**Justification** : Le marché se met à jour toutes les 5 secondes (background task), donc un cache de 5s est parfaitement cohérent.

**Impact** : Réduit drastiquement la charge DB lors de pics d'ordres.

### 3. Cache d'état de simulation (Market Data Service)
**Objectif** : Éviter les lectures/écritures DB pour l'état de simulation (volume, dernière exécution).

**Implémentation** (`market-data-service/src/repository.rs`) :
- Structure : `DashMap<String, MarketSimulationState>`
- TTL : **Permanent** (durée de vie du service)
- Persistance : Batch writes toutes les 100ms

**Impact critique** : **800 queries/sec → 16 queries/sec** (réduction de 98%)

### 4. Cache d'authentification (User Service)
**Objectif** : Éviter les appels bcrypt répétés pour le même utilisateur.

**Implémentation** (`user-service/src/repository.rs`) :
- Structure : `DashMap<String, (UserId, String)>`
- TTL : Permanent (invalidé au logout ou changement de mot de passe)
- Clé : email de l'utilisateur

**Impact** : Accélère les re-authentifications et les validations de session.

## Stratégie de batching des écritures

Complément du cache 3, pour réduire les écritures DB.

**Mécanisme** (`market-data-service/src/repository.rs`) :
- Channel Tokio `mpsc::unbounded` pour collecter les updates
- Buffer en HashMap accumulant les changements par symbole
- Flush périodique toutes les **100ms** OU si buffer > 50 symboles

**Impact** : **800 writes/sec → ~80 writes/sec** (réduction de 90%)

## Conséquences

### Avantages

- **Performance** : Réduction massive de la charge DB (98% sur certains endpoints)
- **Latence** : Temps de réponse réduit de ~500ms à ~50ms sous forte charge
- **Scalabilité** : Le DB n'est plus le goulot d'étranglement
- **Cohérence** : TTL courts garantissent des données récentes

### Inconvénients

- **Mémoire** : Utilisation RAM accrue (acceptable pour le gain)
- **Complexité** : Plusieurs implémentations de cache à maintenir
- **Données périmées** : Possibilité de lire des prix légèrement obsolètes (max 4.5s)
- **Perte au redémarrage** : Cache en mémoire non persisté

### Risques

- **Incohérences** : Cache et DB peuvent diverger temporairement
- **Memory leak** : DashMap permanent doit être surveillé (nombre de symboles limité)
